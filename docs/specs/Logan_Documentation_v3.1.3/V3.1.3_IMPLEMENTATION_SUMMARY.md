# Logan Intelligence — v3.1.3 Implementation Summary
**Version:** 3.1.3
*New in v3.1.3 (2026-08-05). Records the first code-level implementation pass on `logan_core/` following
the documentation-only v3.1.3 reconciliation. Read alongside `18_SESSION_LOG.md`'s 2026-08-05 entry and
`23_CURRENT_IMPLEMENTATION_STATE.md`, which is authoritative on current state — this file is the
narrative record of what changed and why.*

---

## Scope

Two prior sessions produced the v3.1.3 documentation package and its ADR log (ADR-029 through ADR-038).
This session was the first to touch actual code: implementing the approved, additive Sprint 2 contract
foundations in `logan_core/` — not new product decisions, not scoring changes, not a trained model.

Before any code change, the session inspected existing contracts, call sites, fixtures, and the full
28-test baseline (confirmed passing) to ensure compatibility.

## What was implemented

### 1. `MemoryRecord` user isolation (ADR-033)

- `logan_core/contracts/memory.py`: `user_id: str`, required, validated non-empty.
- `logan_core/contracts/common.py`: `LOCAL_FOUNDER_USER_ID = "demo_user"` — names the identifier already
  used informally everywhere (README, test fixtures, the demo endpoint) rather than introducing a new one.
- `logan_core/learning/engine.py`: `LearningEngine.process_feedback()` gains a `user_id` parameter and
  stamps it onto every `MemoryRecord` it creates.
- `logan_core/orchestrator/pipeline.py`: `Orchestrator.run_feedback_loop()`,
  `run_memory_inbox_confirm()`, and `run_memory_inbox_reject()` all gain a `user_id` parameter — none of
  them took one before, so `MemoryRecord`s written through the feedback/Memory Inbox path had no user
  isolation at all until this change.
- No database was chosen; no multi-tenancy infrastructure was built. Independent of ADR-006, which
  remains open.

### 2. Feedback interaction types (approved additions only)

- `logan_core/contracts/feedback.py`: `InteractionType` gains `"watch"` and `"remind"` — the two types
  explicitly approved this pass. `not_relevant`/`already_acted` (documented in `07_DATA_CONTRACTS.md`
  from earlier v3.1.2 work) were **not** added — out of scope for this pass.
- `logan_core/feedback/engine.py`: `FeedbackEngine.interpret()` maps `"watch"` to the same
  `interested`/0.85 tier as `save`/`share`, and `"remind"` to `interested`/0.75 — deterministic
  classification only, no ML behavior of any kind.

### 3. Reserved ML model metadata (ADR-032)

- `logan_core/contracts/trust.py`: `EvidenceTrust.source_reliability_model_version`, default
  `"deterministic-baseline"`.
- `logan_core/contracts/confidence.py`: `ConclusionConfidence.confidence_model_version` (same default)
  and `calibrated_at` (defaults to `null`).
- Purely additive Optional fields. Neither `EvidenceTrustEngine` nor `ConclusionConfidenceEngine` was
  modified — `trust_score`/`confidence_score` are computed by the exact same formulas as before.
  `training_snapshot_id` was **not** added anywhere — no justified location exists for it yet (no
  Calibration/Training Service is implemented), so it was left out rather than placed speculatively.

### 4. `OutcomeRecord` v2 (ADR-036)

- `logan_core/contracts/feedback.py`: `OutcomeRecord.schema_version` is now `"2.0"`. New fields:
  `opportunity_id`, `prediction_id`, `user_id`, `entity_id`, `trigger_event_ids`, `evidence_ids`,
  `prediction_or_claim_type`, `raw_predicted_value`, `created_at`, `evaluation_horizon`, `resolvability`,
  `observed_result`, `invalidation_status`, `invalidation_conditions`, `verification_quality`,
  `source_contribution`, `decision_trace_ref`. The old `result`/`expected` fields are kept, now
  `Optional`, explicitly commented as deprecated in favor of `observed_result`/`raw_predicted_value`;
  `accuracy` is retained as-is. Nothing in `logan_core/` constructed `OutcomeRecord` before this change,
  so nothing broke.
- A `model_validator` enforces `observed_result` is populated if and only if `resolvability == "resolved"`
  — the contract-level guard against fabricating resolved outcomes.
- `EvaluationHorizon` and `VerificationQuality` (shared with `SourceObservation`, below) were added to
  `logan_core/contracts/common.py`, matching the shapes worked out in `OUTCOME_EVALUATION.md`'s example.

**Compatibility deviation, flagged:** `07_DATA_CONTRACTS.md`'s documentation-level table marks
`opportunity_id` as required. In code it is `Optional`, because no Opportunity Lifecycle layer with its
own stable ID exists in `logan_core/` yet (see `23_CURRENT_IMPLEMENTATION_STATE.md`) — nothing could
supply a required value. This is a deliberate, reported deviation, not an oversight.

### 5. `SourceObservation` (new, forward-facing)

- `logan_core/contracts/trust.py`: a source-centric sibling of `OutcomeRecord`, built for a future
  source-reliability calibration pass (ADR-032's approved first ML capability). Same non-win/loss shape
  (`resolvability`, `verification_quality`, `evaluation_horizon`, `observed_result`,
  `invalidation_status`), scoped to a `source_id` + `trigger_or_claim_id` rather than an opportunity.
- **Not wired into `EvidenceTrustEngine`.** Nothing reads or constructs it yet. `EvidenceTrust.source_score`
  and `trust_score` remain computed exactly as before, unaffected by this contract's existence.

### 6. `LearningEngine.process_outcome()` (ADR-036 interface)

- Added as a typed method that immediately `raise`s `NotImplementedError`, with a docstring explaining
  why: no delayed-outcome learning scheduler exists yet (`UNRESOLVED_QUESTIONS.md` #4), and a stub that
  silently returned a placeholder result would misleadingly imply one does. Failing loudly was judged
  safer than a quiet no-op, per this pass's explicit instruction not to create "misleading dead behavior."
- Does not train a model, update weights, alter scoring, change source trust, fabricate verification, or
  write a real `MemoryWrite`.

## What was explicitly *not* done

- **Domain literal unchanged.** `logan_core/contracts/common.py`'s `Domain` literal still has 6 values
  (`stocks, sports, poly, social, news, crypto`). Nothing implemented this pass required `culture` or
  `personal_finance` in code — verified by grep before concluding this.
- **No scoring formula, domain weight, or trained model invented or activated.**
- **`AttentionRecommendation.priority_score` was not renamed in code.** Only the documentation-level
  rename (to `internal_rank_score`, ADR-029) happened in the prior session. Renaming the actual code field
  was not in this pass's task list and would touch scoring-adjacent code broadly (see the finding below).
- **`external_execution_link` was not enabled anywhere** — it doesn't exist in the running `DeliveredItem`
  contract at all yet.
- **No directive financial or betting language was introduced.**

## Findings reported, not fixed (outside this pass's authorized scope)

Both were discovered during the required pre-change inspection, not introduced by this session:

1. **`logan_core/opportunity/engine.py` lets `community.momentum_score` influence `priority_score`** —
   directly via a `dimensions.community_momentum * 0.02` term in the formula, and indirectly via
   `global_importance = momentum_score * 0.5 + confidence_score * 0.5`, which itself feeds
   `opportunity_magnitude`. This was a deliberate, documented V1 design choice
   (`logan_core/docs/IMPLEMENTATION_DECISIONS.md` #4) made **before** ADR-034 existed. It now directly
   conflicts with ADR-034 ("community momentum ... can never influence ... ranking ... or recommendation
   direction"). Fixing it means changing tested scoring behavior (`test_opportunity.py`,
   `test_pipeline_tesla.py`) — explicitly out of this pass's scope ("do not change current scoring
   behavior").
2. **`backend/app/logan_feed.py`'s `DemoFeedResponse` publicly exposes `priority_score`** as a response
   field and sorts results by it — a live instance of ADR-029's "never returned via any public API" rule
   being crossed in the historical prototype. `backend/app/` is explicitly untouched historical code per
   ADR-014 and root `CLAUDE.md`; fixing this would mean editing it, also outside this pass's scope.

Both are recorded here and in `23_CURRENT_IMPLEMENTATION_STATE.md` for an explicit owner decision on a
dedicated follow-up pass — not resolved silently, not resolved unilaterally.

  `pip install -r requirements.txt` — already-declared `pydantic>=2.10`, `pytest>=8.0`, no dependency

- Targeted searches (all clean): no missed `MemoryRecord(` call sites without `user_id`; no stale
  `OutcomeRecord(` construction anywhere in `logan_core/` or `backend/`; no unhandled `interaction_type`
  values in `FeedbackEngine.interpret()`; the two `priority_score`/`community_momentum` findings above
  (reported, not silently left out of the search results).

  intended tools, but no config file or declared dependency for any of them exists in this repository
  today. Not installed without approval — reporting the gap rather than installing blindly, per
  instruction.
